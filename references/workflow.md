# 代码变更检查工作流

## 输入

- 项目目录。
- 需求、设计、任务或待办文档。
- Git、SVN、patch、目录快照或最终代码状态。
- 用户特别关注的业务风险。
- 项目隐式规则，例如内部寻址、权限、状态机、第三方对接规范。
- 指定业务契约文件，或者可作为契约参照的迭代前旧代码。

## 步骤

1. 确认变更来源：Git 优先，其次 SVN；没有版本管理时使用目录快照。优先使用 `--interactive` 让用户用方向键、空格和回车选择本次迭代包含的提交记录。Git 也可通过 `--base-ref` 和 `--target-ref` 检查一次迭代范围，SVN 也可通过 `--svn-revision` 检查版本范围。
2. 确认是否启用 CodeQL：交互模式询问用户；非交互模式使用 `--codeql` 或 `--require-codeql`。
3. 初始化 CodeQL target database：检测 CLI 和语言，对项目当前工作目录创建或复用数据库，执行标准查询并保存 SARIF。
4. 收集需求证据：读取 OpenSpec、spec-kit、superpowers、Markdown、todo 和用户补充说明。
5. 建立需求-提交映射：交互模式下，把用户选中的每个提交关联到需求、任务或关键约束。无法关联的提交和需求都要在报告里暴露。
6. 选择业务契约来源：指定契约文件、迭代前旧代码、两者都用或不使用。
7. 提取候选业务契约：契约文件提取显式规则；旧代码提取寻址、调用参数、租户字段、状态字段等已有约定。
8. 确认业务契约：交互选择本次审计启用的候选契约，避免直接固化历史坏代码。
9. 提取代码证据：合并文本规则命中和 CodeQL SARIF 命中。
10. 生成证据包：使用 JSON 保存原始线索，使用 Markdown 保存人工阅读报告。
11. 人工复核：优先阅读 `critical` 和 `high` 命中位置。
12. 形成结论：明确是否建议合并/发布、需要补测什么、哪些位置需要回退或重做。

## 判断原则

- 先看证据，再做结论。
- 不把“运行不报错”当作质量通过。
- 不把 AI 自评当作审计结果。
- 需求、设计、任务和代码必须能互相追踪。
- 提交记录必须尽量关联到具体需求或任务；没有来源的提交要标成审计风险。
- 指定契约文件优先于旧代码候选契约；旧代码候选契约必须经过用户确认。
- 只要迭代前 baseline 可用，就不能把当前新增代码回退当成旧契约。
- 对旧逻辑和隐式规则保持怀疑，尤其是调用链、寻址、权限和状态流转。
- CodeQL 未启用、不可用或执行失败都必须在报告中明确展示，不能解释为检查通过。
- 当前 CodeQL target database 对应项目当前工作目录，不等同于任意历史提交组合。
