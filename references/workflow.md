# 代码变更检查工作流

## 输入

- 项目目录。
- 需求、设计、任务或待办文档。
- Git、SVN、patch、目录快照或最终代码状态。
- 用户特别关注的业务风险。
- 项目隐式规则，例如内部寻址、权限、状态机、第三方对接规范。
- 指定业务契约文件，或者可作为契约参照的迭代前旧代码。

## 步骤

1. 识别仓库上下文：使用 `--print-context` 从当前目录向上、向下识别 Git、SVN 和推荐审计根目录。检测到 `svn-incompatible` 时不得静默改用目录快照。
2. 确认实际审计范围：确认代码子项目、Git/SVN 版本范围、需求文档、契约来源、CodeQL 和输出目录。用户选择子项目时，后续 `project` 必须使用该子项目路径；只选择部分需求或契约时使用 `--strict-spec` 或 `--strict-contract`。
3. 锁定审计计划：无 TTY 的 AI 编程工具必须先使用 `--save-audit-plan` 生成计划，向用户展示计划内容，获得确认后再使用 `--confirm-audit-plan`。最终执行只允许使用 `--audit-plan`；确认后的计划被修改时会拒绝执行。
4. 确认变更来源：Git 优先，其次 SVN；没有版本管理或用户明确选择目录快照时才使用 `--scan-all`。真实终端直接运行 Python 脚本时可以进入交互，让用户用方向键、空格和回车选择本次迭代包含的提交记录。
5. 初始化 CodeQL baseline/target 分析：可靠构造两个代码状态，先提取轻量语义清单；CodeQL CLI 可用时再创建或复用数据库，执行标准查询、自定义语义查询并保存 SARIF。Maven/Gradle Java 项目默认使用 `autobuild`。
6. 收集需求证据：只读取计划内的 OpenSpec、spec-kit、superpowers、Markdown、todo 和用户补充说明。
7. 建立需求-提交映射：把用户选中的每个提交关联到需求、任务或关键约束。无法关联的提交和需求都要在报告里暴露。
8. 选择业务契约来源：指定契约文件、迭代前旧代码、两者都用或不使用。
9. 提取候选业务契约：契约文件提取显式规则；旧代码提取寻址、调用参数、租户字段、状态字段等已有约定。
10. 确认业务契约：交互选择本次审计启用的候选契约，避免直接固化历史坏代码。
11. 执行业务契约：将启用契约和 target 语义清单对比，生成契约违反项；JSON 契约只有在提供同文件名实际响应快照时才执行字段路径对比，否则记录为未检查。
12. 提取代码证据：合并文本规则命中、契约违反项和 target CodeQL SARIF 命中，将 CodeQL 命中分为新增、已有和已消失，并对比 baseline/target 的调用参数、寻址、租户字段和状态字段线索。测试、文档、调试日志、fixture 和 XML namespace 的文本命中默认移入已抑制线索区。
13. 生成证据包：使用 JSON 保存原始线索，使用 Markdown 保存人工阅读报告，并记录实际生效的审计计划。
14. 人工复核：优先阅读 `critical` 和 `high` 命中位置。
15. 形成结论：明确是否建议合并/发布、需要补测什么、哪些位置需要回退或重做。

## 判断原则

- 先看证据，再做结论。
- 不把“运行不报错”当作质量通过。
- 不把 AI 自评当作审计结果。
- 需求、设计、任务和代码必须能互相追踪。
- 提交记录必须尽量关联到具体需求或任务；没有来源的提交要标成审计风险。
- 指定契约文件优先于旧代码候选契约；旧代码候选契约必须经过用户确认。
- 只要迭代前 baseline 可用，就不能把当前新增代码回退当成旧契约。
- 已启用的业务契约必须进入执行检查；无法执行的契约仍保留在报告中，作为人工复核线索。
- 对旧逻辑和隐式规则保持怀疑，尤其是调用链、寻址、权限和状态流转。
- CodeQL 未启用、不可用或执行失败都必须在报告中明确展示，不能解释为检查通过。
- 交互模式下用户启用 CodeQL 但本机没有 CodeQL CLI 时，必须提示安装方式或跳过本次 CodeQL 分析。
- 只有 baseline 和 target CodeQL 分析都成功时，才允许生成新增、已有和已消失分类。
- Git 显式范围、连续选中提交、Git 工作区和目录快照支持 CodeQL 对比；非连续 Git 提交和 SVN 暂时降级为 target-only。
- 轻量语义清单用于 CodeQL 不可用时的降级检查，只能提供风险线索，不能代替语言级 AST、编译器或真实运行验证。
