# 审计覆盖质量闸门设计

## 背景

两次真实审计记录暴露出同一类漏报链路：

- 第一次审计同时读取 OpenSpec 和 `docs/api-mock-backup/*.json`，审查 AI 继续精读相关实现，发现了 `/safetyInspection` 缺少列表字段和 `handleRate.label` 错位。
- 第二次审计只选择两个 OpenSpec change 作为契约，59 条自然语言契约全部未检查；流程仍直接进入普通报告解读，没有继续按契约反查实现，因此漏掉已知问题。
- 第二次审计建议把期望契约 JSON 当作 `--response-snapshot`，如果照做，可能用同一份期望数据与自身比较，产生虚假通过。
- 第二次审计使用 `--scan-all` 扫描整个后端，通用风险淹没了所选 change 的业务风险。
- Maven Java 项目被显式指定 `--codeql-build-mode none`，导致本可使用 `autobuild` 的 CodeQL 建库失败。

## 目标

建立确定性的审计覆盖质量闸门，使工具和 Skill 在证据不足时不能给出“看起来完成”的普通结论，并为未检查契约生成可执行的人工核验任务。

## 设计

### 1. 审计计划预警

生成审计计划时增加 `review_warnings`：

- `--scan-all` 无法区分本次迭代新增与历史代码。
- 契约输入仅有自然语言文档，但文档引用了未纳入的 JSON 契约材料。
- 期望契约与实际响应快照路径相同或内容相同。
- Maven/Gradle Java 项目显式使用 `--codeql-build-mode none`。

存在高风险预警时，AI 必须先向用户解释并修正计划，不能直接请求确认。

### 2. 输入角色校验

契约 JSON 表示期望结果，`--response-snapshot` 表示运行时实际响应。两者路径相同或内容相同时：

- 将其记录为输入角色冲突。
- 冲突快照不参与契约比较。
- 对应 JSON 契约保持“未检查”，禁止虚假通过。

### 3. 引用契约材料发现

从选中的需求、设计、任务和契约 Markdown 中识别 `.json` 路径或 `*.json` 引用，并从项目目录及其父级查找实际文件。

发现被文档引用、但未纳入契约输入的 JSON 文件时：

- 写入 `missing_referenced_contract_artifacts`。
- 审计覆盖质量闸门至少为 `partial`。
- 如果自动契约覆盖率同时为 0%，质量闸门为 `blocked`。

### 4. 未检查契约人工核验任务

对每条未检查契约：

- 从契约文本提取接口名、方法名、字段名等代码标识符。
- 在生产源码中反查候选实现位置。
- 生成 `manual_review_obligations`，包含契约来源、未检查原因、搜索标识符和候选代码位置。

Markdown 报告将这些任务放在普通风险清单之前，要求审查 AI 优先交叉核验契约与代码。

### 5. 审计覆盖质量闸门

新增 `audit_coverage`：

- `success`：没有关键覆盖缺口。
- `partial`：存在全量扫描、部分未检查契约、缺失引用材料或 CodeQL 失败。
- `blocked`：自动契约覆盖率为 0%，或存在契约/响应快照角色冲突。

质量闸门只限制结论可信度，不阻止生成证据包和报告。

### 6. Skill 最终解读规则

当质量闸门不是 `success` 时：

- 不得用“未发现风险”或“可以合并”结束审计。
- 必须先核验高优先级 `manual_review_obligations`。
- 高风险项必须同时包含契约证据、代码证据、偏差说明、影响和验证方式。
- 与所选需求无关的通用正则命中只能放入补充风险，不能替代业务高风险清单。
- Maven/Gradle Java 项目不得显式选择 `none`；应使用自动模式或 `autobuild`。

## 非目标

- 本轮不尝试自动理解任意 Java 方法构造出的完整运行时 JSON。
- 本轮不把自然语言契约自动转换成任意可执行规则。
- 本轮不自动把引用材料加入用户已确认的审计范围，只提示并要求确认。
